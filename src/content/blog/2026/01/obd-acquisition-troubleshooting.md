차량의 동역학 데이터(악셀, 브레이크, 차량 속도 등) 수집을 목적으로 PCAN to OBD 케이블을 활용해 통신 파이프라인을 구축했다. 초기에는 PEAK사 공식 OBD Viewer와 PCAN-View로 통신 상태를 점검했다. 그러나 기본 제공되는 OBD Viewer는 표준 PID만 조회할 수 있었고, 제어 계통의 비표준 확장 PID 데이터는 확인이 불가능했다. 이에 필요한 센서 데이터 PID를 특정하고자 브루트포스 스캔 환경을 구축했다.

## [통신 파이프라인] 확장 PID 브루트포스 스캔의 한계

특정 조작(예: 브레이크 페달 조작 전후) 전후 데이터를 비교해 목적 PID를 찾으려면 스크립트 기반 자동화가 필수였다. PEAK사 PCAN-View는 수동 조작 툴이어서 브루트포스 스캔과 수신 응답 로깅에 적합하지 않았다.

- `python-can` 패키지를 이용해 유효한 확장 PID를 탐색하는 자동화 스크립트를 작성했다.
- 스크립트를 차량에 연결해 테스트한 결과, 차량에서 수신되는 응답 데이터가 계속해서 손상되었다.
- 물리적 연결이 유지된 상태에서 공식 툴인 PCAN-View로 진단 세션 시작 메시지를 전송하면 정상 응답이 수신되는 점을 감안해, 문제 원인을 프로토콜 처리 상의 한계로 보았다.
- `python-can` 같은 범용 라이브러리 환경만으로는 복잡한 차량 진단 프로토콜 요구사항을 완벽히 제어하지 못해 통신 불안정이 발생한다고 판단했다.

## [프로토콜] PCAN-OBDonUDS API 기반 통신 안정성 확보

범용 라이브러리 자체 구현에 한계가 뚜렷해, 신뢰성 있는 통신 계층을 확보하고자 PEAK사 공식 API 환경으로 전환했다.

- PEAK사가 제공하는 `PCAN-OBDonUDS` API를 도입해 진단 프로토콜 통신을 처리하도록 구조를 바꿨다.
- 해당 API가 Windows 전용이라 기존 Linux 환경을 쓸 수 없는 물리적 제약이 따랐으나, 프로토콜 안정성과 빠른 데이터 검증을 최우선으로 삼아 Windows 환경으로 전환했다.
- 개발 전 PCAN-ISO-TP, PCAN-OBD-2, PCAN-OBDonUDS, PCAN-UDS, PCAN-Basic 등 주요 API 매뉴얼을 분석해 통신 규격을 확인했다.
- 이를 토대로 C++ 환경에서 안정적으로 확장 PID를 스캔하고, 차량 응답을 유실 없이 기록하는 데이터 수집 프로그램 초안을 완성했다.
